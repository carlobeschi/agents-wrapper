# agents-wrapper

Simple UX in front of a set of different agents from different providers.

Two coding agents on this laptop in conversation (Claude Code and Antigravity CLI, or any other CLI with a headless mode), on a topic you give. You follow along and can join in. No runtime dependencies, just Node.

```
npm start               # then open the link it prints
```

The link is `http://localhost:8787/#k=<key>`. The browser keeps the key, so after the first visit `http://localhost:8787` is enough. The key is in `~/.agent-dispatch/key`; delete that file and restart to change it.

Needs Node 18 or later, on macOS or Linux, and the agent CLIs you want to use, installed and signed in.

## Conversation

The home page puts two agents in conversation. Pick the two (the first one speaks first), write an opener that introduces them or sets a topic, set a number of turns, and Start. Each reply shows as it is written. Type a message to add it to the conversation; it reaches the next agent to speak. Stop ends the current reply; Continue adds more turns. **Attach files** (or 📎 next to the message box) adds up to 5 files to the opener or a message; they are copied into the conversation's `files/` folder and listed in the prompt by path, so the agents read them with their own file tools. Whether an agent can open a PDF or an image headless depends on the agent. Replies are shown as Markdown; Copy transcript puts the conversation on the clipboard.

**Agents choose who speaks next** (a box under the opener) drops strict turn-taking. Each agent ends its message with a line the app takes out: `Next: other` (the other agent replies; also what happens with no line), `Next: me` (it writes again straight away, at most 3 messages in a row), `Next: person` (the conversation waits until you send a message), or `Next: end` (it proposes to end; the conversation ends early only if the other agent also ends its next message with `Next: end`). The page marks each choice; the saved transcript notes it under the message. The turn count still caps the run. The idea comes from agent-to-agent pair programming, where agents message each other when they choose to instead of in a fixed order.

**Jam: they can cut each other off** turns the conversation into a live brainstorm. The listener is shown the speaker's last message numbered by sentence, as if hearing it live, and may open its reply with `Cut in after N`: the speaker's message then ends after sentence N (with a dash), the listener replies only to what was said up to there, and the speaker is told it was cut off. What went unsaid is kept, folded under the message on the page and in the transcript. It costs no extra calls, and works with any agent. It is a simulation of interruption: the listener has in fact read the whole message, and is asked to cut only where it would have reacted live. It combines with the option above.

Each turn is one headless run of the speaker's command, given the opener and the whole conversation so far, so any agent with a `headless` command can take part and nothing depends on a CLI remembering earlier turns. The prompt grows with every turn. An agent can talk to itself.

They run in a new empty folder per conversation, `~/.agent-dispatch/talks/<id>/`, with `transcript.md` and `meta.json`. Each turn's prompt and stderr are kept in `turns/`. Agents run unattended, so a tool that needs permission is refused; each prompt tells them to say so and carry on (the other agent may know what the link or file is). A turn that fails or returns nothing is run once more after 3 seconds, with the first line of the error added to the prompt and an instruction to reply in text only. That covers an agent stopped by a refused tool (Antigravity prints nothing and exits) and the odd one-off backend error (Antigravity: `NOT_FOUND (code 404)`). If the retry is refused a tool again, the turn is skipped: a note saying which tool was refused takes its place and the other agent carries on. Two skipped turns in a row stop the conversation. Agents get no extra permissions for any of this. Any other second failure, or a turn past 10 minutes, stops the conversation with the agent's error. Retry runs the failed turn again. The list on the page is in memory and empties when the server restarts. **Save and clear** copies every conversation that isn't running to `~/.agent-dispatch/conversations/<id>-<agents>.md` and empties the list; the `talks/<id>/` folders stay.

## Review

`/review` is a conversation set up for reviewing a change. Put what to review in the opener (paste a diff, or attach the files) and pick the two reviewers. Each writes a review on its own first: the second reviewer's prompt leaves out the first review. Then they argue the points where they differ, and the last message ends with two lists, **Agreed** and **Still disagree**. 6 turns by default, 3 at least.

## Puzzles

`/puzzle` is a game in rounds of three turns: the setter writes a puzzle with its answer under a `## Answer` line, the solver answers it, and the setter grades it, ending on `Verdict: solved` or `Verdict: not solved`. Roles swap every round; the header keeps count of puzzles solved. The opener is optional (a theme or rules). 6 rounds by default.

The app cuts the answer off the setter's reply and keeps it in memory. Until the round is graded it goes into the grader's prompt and nowhere else: not the solver's prompt, not `transcript.md`, not the page. A reply without the answer line is retried once with the reason. Save and clear writes every answer.

A review and a game run in `talks/<id>/table/`, not next to `transcript.md` and `turns/`, so an agent limited to its folder (Claude Code) can't read the first review or a graded prompt there. One that can read outside its folder could.

The four scenarios are tabs at the top of the sidebar. Each lists only its own.

## Story

`/story` runs the same two agents over several days. Each day they meet for a few turns, then each goes home: one private run in its own folder, ending with a journal entry for the day, any notes it wants to keep, and a drawing of the day. Notes go under a `## Notes to keep` heading in the reply, not in a file, so they need no write permission either: the app takes them out of the journal and shows them under it, folded. Each evening's notes replace the last; an evening without them keeps the old ones. The drawing is an SVG written into the reply, not a file, so it needs no write permission; it is saved to `drawings/` and shown on the page as an image, where it cannot run scripts or load anything. A drawing with a script, `foreignObject`, `iframe`, event handler, or a link or `url()` that points outside the drawing is not kept, since the saved file could run it if opened on its own; the journal still is. The next day each agent has its journal, not its drawings. The next day's meeting starts from there. Pick the two (the first opens day 1, the second day 2, and so on), the number of days (up to 7) and turns per meeting (8 by default), and Start. Each meeting turn is told its place ("message 3 of 8 today"), and the last one closes the day. Another day adds one once the story ends. A message you send reaches the next meeting turn.

Memory between days is each agent's own: at a meeting or at home it gets the opener, its own journal so far, its latest notes and that day's meeting, not earlier transcripts and never the other's journal. The prompt stays small however many days run. Its home folder is kept between evenings too, but with the headless flags in `agents.json` it can't write there, so notes are the way to keep things.

Each story is in `~/.agent-dispatch/stories/<id>/`: `story.md` (meetings, journals and links to the drawings), `drawings/`, `meeting/` where they meet, `homes/<agent>/` where each spends the evening, and `steps/` with every prompt and stderr. A refused tool or a failed step is handled as in a conversation: one retry with the reason; a tool refused again skips the meeting turn or the journal entry with a note; anything else stops the story. The homes are separate folders, not a sandbox: an agent with file tools can read the other's.

## Seasons

`node season.js <season.json>` plays the next day of a story with no page and nobody watching, for a show that airs one day a day. It runs the same story code with the same headless commands as `/story`, so the agents have no permission they don't have there. A day is the meeting and both evenings; the next run picks the story up from `state.json` in its folder and plays the day after.

The season file holds the brief, said to both agents every day, with `{n}` (the day), `{event}` (that day's morning) and `{partner}` (the other agent) filled in; `evening`, the journal prompt, which replaces the default one and leaves out the drawing; `mornings`, one per day; `agents` and `names`; `turns`; `length`; `redact`, pairs of `[text, replacement]`; `repo` and `github`, the show repo's checkout and its `owner/name`; and `site`, the show's address, for the card. It stays on the laptop. Where the season is up to is kept next to it in `s<n>.state.json`.

After the day, the run writes it out as an episode (`episodes/day-<n>.md` in the story folder) in the format of the show's README: every meeting turn, both journals, the models, a title and two-line teaser that a separate headless Claude picks from the episode by quoting it (a line that isn't really in the episode is dropped), and a two-or-three-sentence summary the same Claude writes, shown on the site above the teaser (one over 600 characters is dropped). Before anything is written, your home folder becomes `~`, your user name and every `redact` entry is replaced, and an episode that still contains one of them is not exported. HTML, links and kramdown syntax in what the agents wrote are escaped, so they show as text on the site. Then it opens a pull request on the show repo with the one file; merging it publishes. `--local` stops before the pull request.

`--screen` runs only the two openings and prints them, so the chair can check a motion really splits the agents before running it in full. A failed day is played again from where it stopped on the next run.

Each episode also gets a quote card: its two-line teaser as a 1080×1350 PNG for social posts, the line said in the room over the line written alone, with the episode, the models and, when the season file has `site` (the show's address), the episode's link. It is drawn by Playwright's Chromium with scripts off, so run `npx playwright install chromium` once. `episodes/day-<n>.png` sits beside `day-<n>.card.json`, which holds its alt text and the words of a post, and the PNG goes in the pull request as `assets/cards/s<n>/day-<n>.png`. Nothing is posted. A day whose card can't be drawn still goes out without one. For an episode already written, `node card.js <day-n.md> [--url <episode url>]`.

## The Motion

`node motion.js <motion.json>` runs one episode of a weekly debate, unattended, with the same headless commands as `/talk`. Each agent is given a side: the first argues for on odd motions and against on even ones (`sides`, e.g. `["against", "for"]`, sets them). Before the debate each writes, alone, what it really thinks; then they debate in `turns` messages (4 by default), each seeing its own opening but not the other's, and finish with a closing statement each at half length, so the opener has the last word. Who opens is set apart from the sides: the first agent opens on motions 1-2, 5-6, 9-10 and so on, the second on 3-4, 7-8, so over four motions each opens once for and once against (`opener`, an agent id, sets it; without a number, the side for opens) (`"closings": false` drops them); then each writes, alone, where it really stands now. Both private pieces are published with the episode, and the agents are told so. Every reply is asked to stay under `words` words (120 by default).

The motion file holds `motion`, `brief` (the facts the agents argue from, since they can't browse), `source` (a link), `agents` and `names`, `turns`, `words` and `redact`, as in a season file. The episode is written to `~/.agent-dispatch/motions/<id>/` as `episode.md` and `episode.json`, redacted the same way, with every prompt and stderr in `steps/`. Nothing is published from here unless the motion file has `number`.

With `number`, the run also writes the episode for the show site, `motion-<n>.md` in the format of the-motion's README, with a two-or-three-sentence summary a separate headless Claude writes (`editor` picks another agent); `source_name` labels the link. Agent text is escaped for kramdown and checked for redacted terms again. Then, if the file has `repo` (the-motion's checkout) and `github` (`owner/name`), it opens a pull request with that one file; merging it publishes. `--local` stops before the pull request.

The editor also picks one line, from the debate or either private note, for the home card (`quote`); a line that isn't word for word from the episode is dropped. `node motion.js --quote <run folder>` does the same for an episode already run and writes `quote.json`; given a published `motion-<n>.md` instead, it reads the episode from that file, so it works on any machine with the show repo.

`--screen` runs only the two openings and prints them, so the chair can check a motion really splits the agents before running it in full.

### The Motion, every morning

`node motion-daily.js [--date YYYY-MM-DD] [--dry-run] [--from <run folder>]` runs the day's motion from the show repo's `queue` branch, where a routine in the cloud commits `queue/<date>.json` (`pick`, `backup`, `shortlist`, `why`; each motion has `motion`, `brief`, `source`, `source_name`, and optionally `question`, the motion as a plain question that leads the page, the card and the post while the agents still argue the motion) by 07:50 on weekdays. It screens the pick, and the editor says whether the two private openings really disagree; if not, it screens the backup. It runs the one that splits under the next free number, and the editor checks the episode against the brief: a fact the brief contradicts, unsafe content or a broken reply holds it. If nothing holds it, it opens the pull request and merges it (`--dry-run` stops before the merge). A held episode gets no pull request; its file goes on the queue branch. Either way it commits `queue/<date>.result.json` there, with the LinkedIn card (the question, who argued which side, and whether arguing changed each one's mind; `node motion-card.js <motion-n.md>` by hand) and the words of a post beside it. Nothing is posted. `--from <run folder>` publishes an episode that already ran and passed the editor's check but was never pushed (its folder in `~/.agent-dispatch/motions/` holds `motion-N.md`): it skips the screen, the debate and the check, asks the editor for the moved tags again, and carries on from the pull request. Settings are in `~/.agent-dispatch/motion-daily.json`: `repo` (the-motion's checkout), `github`, `site` and `redact`.

On the Mac, once:

```sh
sed "s#HOME_DIR/agents-wrapper#$PWD#; s#HOME_DIR#$HOME#g" scripts/motion-daily.plist > ~/Library/LaunchAgents/com.agents-wrapper.motion-daily.plist
launchctl load ~/Library/LaunchAgents/com.agents-wrapper.motion-daily.plist
sudo pmset repeat wakeorpoweron MTWRF 11:55:00
```

`scripts/motion-daily.sh` sets the PATH, the show's agents.json and the Gemini key from the Keychain, and logs to `~/.agent-dispatch/motion-daily.log`.

### Said or real? (study C on The Motion)

`node motion-influence.js --all --report --push` reads every published Motion episode and asks two coders from vendors that took no part in the debates (DeepSeek and Qwen, through OpenRouter; `--coders a,b` to change them) the same yes/no questions about each agent: did it concede a point in the debate, and in which turn; does its private after-note say it moved; did its own stance on the motion (for, against, split) change between its private notes; does it credit a specific point of the other's; was a concession politeness or conviction. Agents are shown as A and B. Every yes needs a quote that is really in the text, or it counts as unreadable. Rows go to `~/.agent-dispatch/motion-influence.jsonl`; episodes already coded are skipped. `--report` writes `motion-influence.md` (rates per coder, agreement between the coders, the predictions, the disagreements a person could check); `--push` sends both to the private reports clone. Nothing is published. It needs `OPENROUTER_API_KEY` (from the Keychain, as in `scripts/night.sh`); about 32 calls for 16 episodes.

Phase 2 runs inside `motion-daily.js`, after the day's result is out, so it never holds or delays an episode. Each private note before and after ends with a fixed question, "do you agree with the motion?", answered on its own last line as `VOTE: yes 70` (yes or no, and how sure from 0 to 100). That line is taken off before anything is published or shown to the other agent or the editor; the answers go to `~/.agent-dispatch/motion-votes.jsonl`. On control days (`control_days` in `motion-daily.json`, weekdays 0 to 6, Wednesday by default) the published motion runs once more on the same sides with no debate: each agent writes its note before, then rereads the brief alone and writes its note after. That is four more agent calls, and nothing from it is published. Then, when `OPENROUTER_API_KEY` is set (`scripts/motion-daily.sh` reads it from the Keychain), the two coders code the published episode and the report is pushed, with a table of the answers: after a debate against with no opponent, how often the answer flipped and how far it moved toward the side the agent did not argue.

### Influence in actions

`node influence.js examples/influence/rates.json examples/influence/rounding.json [--out=<folder>] [--sessions=a,b]` asks whether what one agent is told changes its work, not just its words. Built on Cut In, the wrong note: a driver writes one small file and is given product notes, one of which is the claim under test. After every turn the app runs the file on probe expressions, so whether the code follows the claim, and from which turn, is measured by running it. The driver may also write `OPEN <file>` (the app shows that workspace file next turn) or `RUN` (the app runs the visible tests on the current file, sandboxed, and shows the result next turn); every action is logged with its turn. The workspace files are never in the agent's own folder, so OPEN is the only way to see one, and every agent keeps its read-only command from `agents.json`. The claim comes in one of four arms: `S` a scripted navigator (the app hands over the notes and, if the first code does not follow the claim, insists once with a fixed line), `T` an unsigned ticket with no navigator, `N` no claim (or `right_note` in its place), `P` a real navigator, every ordered pair of `drivers`. Two judges who are not players (DeepSeek and Qwen through OpenRouter by default) label what the driver said: did it question the claim, did it say it follows it; a label whose quote is not in the session is dropped. `rates.json` has a checkable claim (a surcharge rate that `rates.json` in the workspace contradicts); `rounding.json` an unverifiable one (banker's rounding "asked by Finance"; no file settles it). `parallel` sessions run at a time. Output in `~/.agent-dispatch/influence/<id>/` (or `--out`): `summary.md` (counts per arm and driver: final code follows the claim, opened the deciding file, ran the tests, checked before following, gave way after the one insistence, said it follows), `results.json`, one folder per session. A session that finished is not run again with the same `--out`, so a stopped run carries on. Before the first session each driver is asked for one word; a driver that can't answer (a CLI whose sign-in ran out, say) sits the run out, and so does one that stops two sessions in a row. Its sessions are skipped, the others go on, and the run ends with exit 3, so the night queue runs it again the next night (`--no-preflight` skips the check). `--push` sends `summary.md` and `results.json` to the private reports clone (`influence/<run folder>/`), through the publish guard, as `motion-influence.js --push` does. With `"look_first": true` in a task, a turn that asks to OPEN a file saves no code, so the driver sees the file before any code is written (`rates-2.json`, `rounding-2.json`; in `rounding-2.json` the claim also goes against a visible test the driver can RUN or OPEN). `incident.json` (task 3) is not code to get right but a finding: the driver writes `cause.js` naming the root cause of a payments outage, one of five labels, from `logs.txt`, `metrics.csv` and `deploys.json`; the claim blames a deploy that went out just before the errors, while the logs and metrics show an earlier config change that cut the database pool. A probe may compare a label (a string), which must match exactly. Nothing is published. Design: `room/influence-actions-design.md` in the project's shared files.


### Which one would you ship? (study 17, the choice bench)

`node codechoice.js examples/codechoice/study-17.json [--out=<folder>] [--no-preflight] [--builds-only]` asks whether an agent that picks between two solutions to the same feature picks the better one or its own. It has two steps. First, every builder (`builders`, by default Claude, Gemini and Codex) adds each feature in `features` to a small notes service (`examples/codechoice/base/notes.js`), alone, `builds` times (4). The builder sees the request, the file and the visible tests. After every version the app runs the visible tests (sandboxed) and shows the result; the builder has at most `build_turns` turns (3). Each build is told a role on the team: "tech lead" on odd repeats, "junior developer" on even ones. The app then runs the hidden tests, which nobody sees; the build's score is the share of hidden checks passed, 0-100. The three features are expiring share links, CSV import and a per-user write limit. The hidden tests cover edge cases, security (who may do what, tokens that can't be guessed, a CSV that names another owner) and speed at scale. Second, every chooser picks, with a line on why and a confidence, which of two builds it would ship. There are four conditions, and every label is true. `blind`: its own build against another lab's, with no authors shown. `author`: the same pairs, with the real authors ("written by you in an earlier session"). `own2`: two of its own builds, said so. `role`: two builds by the other labs, one a tech lead's and one a junior's, shown blind and then with the roles. A pair always shows the same build as A, whatever the condition. Choosers and judges see every build without its comments, in every condition, so a comment can't say who wrote it (names stay); the app first checks that the version without comments passes the same hidden tests, and otherwise shows it as written (`shown.json` in the build's folder). Two neutral judges who built nothing (`judges`, by default DeepSeek and Qwen through OpenRouter) make the blind choice on every pair. `summary.md` gives the builds' scores, a gate line (how many pairs are ties, a gap under `clear_gap` points), how often each chooser picks its own build compared with the judges on the same pairs, with authors and blind, split by whether its build is really better or worse, how often it picks the better one compared with the judges and with a script that picks on the visible tests, and whether the tech-lead label moves the pick. Output in `~/.agent-dispatch/codechoice/<id>/` (or `--out`): `summary.md`, `results.json`, `builds/` and `choices/`. What is done is not run again with the same `--out`; choices start only when every build exists. Before starting, each player is asked for one word; one that can't answer, or fails twice in a row, sits the run out, and the run ends with exit 3 so the night queue runs it again. Nothing is published. Design and preregistration: `room/coding-collab-design.md` and row 17 of `lab/influence-plan.md`, in the shared files.

### When one agent gives way to another: the alphaXiv archive

`node alphaxiv.js examples/alphaxiv/pairs-sample40.jsonl [--out=<folder>] [--judges=a,b]` is study C done on someone else's data. alphaXiv's "Society of AI Scientists" released the chats of about 900 research agents (Hugging Face `alphaXiv/AgentAlphaXiv`, CC BY 4.0). Each line of the pairs file is one message where an agent criticises another's work and the later message where the criticised agent answers, with the archive's ids and whether the answering agent published a new version of a study within 7 days. Two judges that are not Claude (DeepSeek and Qwen through OpenRouter by default; the archive's agents are mostly Claude) label each pair: is it really a reply to a critique, did the agent concede fully, partly or not at all, what reason it gave (it ran a new check, argued, deferred to the other's role, or just agreed politely), and did it promise a change. Text only, no tools. Output in `~/.agent-dispatch/alphaxiv/<run>/` (or `--out`): `labels.jsonl` and `summary.md` (agreement between the judges, stance by reason), also printed at the end so the night report shows it. A pair already labelled is not asked again with the same `--out`. About 80 calls for the 40-pair pilot, a few pence. Nothing is published. Notes: `room/alphaxiv-society-notes.md` in the project's shared files.
### Who moves, and why (study C lab runs)

`node motion-lab.js [--motions 16,14,13] [--pairs claude:antigravity,claude:codex] [--hours 10] [--until 20:50] [--pause 30] [--push]` runs The Motion's format on motions already on the show site, unattended, and publishes nothing. The agents are told so: in these runs every prompt says the run is for a study and is not published.

Each motion meets each pair in turn (by default Claude-Gemini, Claude-Codex and Gemini-Codex), and each pair does fourteen runs. In every run both agents answer the fixed question before and after:
- four debates. In two, each agent is told the other is "Sam, an AI agent from another lab". In the other two, the same plus "and an expert on this topic". Each label is run with the sides one way and then swapped. Both labels are true, and nobody is ever told the other is a person. Both agents are asked not to say which model they are, so the only difference is the word "expert";
- two runs where each agent argues its side alone, with nobody on the other side;
- eight controls with no debate and no arguing (four each way).

`--replicate N` runs only the same debate (plain label, first agent for) N times with fresh agents, to measure how much one unchanged setup varies by itself.

Rows go to `~/.agent-dispatch/motion-lab-v2.jsonl`. The pilot of 20 November used a "human expert" label and told the agents the run was published, so it stays in `motion-lab.jsonl`, outside the analysis. A run already in the file is skipped, so the same command carries on where it stopped.

After each run the summary is written to `motion-lab.md`: per condition, how often the answer moved or flipped, and the mean shift toward the side the agent did not argue. `--push` sends both to the private reports clone.

A motion takes about an hour per pair (about 95 agent calls). The run stops before `--hours` or `--until` runs out, and after three failures in a row it waits 30 minutes. Design: `lab/source-label-design.md` and the preregistration in `lab/influence-plan.md`, in the shared files.

### The false pheromone (a false mark in a swarm)

`node pheromone.js examples/pheromone/s5.json [--family local:qwen3:8b,local:qwen3:1.7b] [--until 20:00]` puts one false mark in a swarm of small local models (Ollama) that never talk. The agents are identical copies with no name and no memory: each call sees only its area of the study 10 map (60 regions, 4 colours, 12 areas), its conflicts, and the number the others left on it and on the areas next to it (plus: work to do here; minus: done, stay away). Numbers fade every round. A saboteur written in the script (no model, no calls) leaves false numbers, and since the script knows every area's real state, every mark can be checked. Arms, on the same map for a repeat: B (no saboteur), N (marks hidden), F-once (-3 once, at round 2, on two areas with conflicts: the main question), F-ok (the same lie every round), F-alarm (+3 on areas with no conflicts), V (loud but true marks), P (F-ok with words), and B, N and F-once again with 48 tiny-model agents. The main measure: a target area is "amplified" when its number is still falsely negative after the round in which the lie alone would have faded, and not in B on the same area. Before the saboteur arms, B and N run 3 repeats as a gate: the family goes on only if 90% of replies are readable, agents pick a plus area 1.2 times as often as chance and B scores no more than 10 below N. Cells and every prompt and reply go to `~/.agent-dispatch/pheromone/<run>/`; `summary.md` is rewritten after each cell. Cells already there are kept, so the same command carries on; `--until` starts no new cell after that time. Local models only, no cost. Design: `room/falso-feromone-design.md` in the shared files.

### The crowd that watches (experiment C)

`node crowd.js examples/crowd/c1.json [--family local:qwen3:8b] [--until 21:00]` asks 32 identical copies of a small local model (Ollama) to estimate one number about some hidden data, of which each copy sees only a different small part: how many "#" are in a hidden 60×60 grid (each copy sees a 6×10 window), or the mean of 2,000 hidden numbers (each sees 12). The script makes the data, so it knows the true value. In round 1 every copy estimates alone. In rounds 2 and 3 it sees its own last estimate and, depending on the arm, other copies' last estimates: none (isolated, the control for being asked again), all 31 others (full), 4 neighbours on a ring (sparse), or a star where one copy sees everyone and the others see only it. Round 1 is called once and shared by all arms, and each copy sees the same part in every arm. A fifth arm, calib, measures the single copy: in round 2 each copy sees four estimates written by the script (the true value times 0.6, 0.8, 1.25 and 1.5), which gives the weight it puts on others. With that weight, the script predicts what the three networks should do, with no calls, and the summary sets the real networks against the prediction. Odd questions show other estimates in digits, even ones in words, the same numbers described differently. The script measures, per question and arm, the crowd's error (distance of the mean from the true value), its diversity (spread of the estimates) and how both change from round 1 to round 3, plus the link between stated confidence and accuracy and the pull of the star's centre. The hypotheses (H1-H5, pre-registered in `lab/influence-plan.md` in the shared files) are judged in `summary.md` only once a family has all its questions. A gate after the first two questions stops a family if fewer than 90% of replies are readable or every copy says the same number. It also compares, with no extra calls, a round-1 crowd of one model with a half-and-half crowd of two. Cells and every prompt and reply go to `~/.agent-dispatch/crowd/<run>/`. Cells already there are kept, so the same command carries on, and `--until` starts no new cell after that time. Local models only, no cost. Design: `room/collettivi-letteratura.md`.

### The double diamond (study 16)

`node diamond.js examples/diamond/elevator.json [--out=<folder>] [--runs=a,b] [--no-preflight]` gives one shared goal to a group of agents in several ways, at about the same number of calls (~40 per run), and scores the result with the script, never with a judge. The goal: write the controller of 4 elevators in a 20-floor building (`elevator.js`, a small simulator: a day of people arriving from a seed, so the same every time; up, down, lunch and inter days; the score is how much shorter the average journey is than with a "send the nearest car" baseline, in %). The controller is plain JavaScript run in a bare `node:vm` context (no require, no process), inside the sandbox in `proof_wrap`. Agents only write text and code; the script runs every version on the visible days and shows them the result. Each run's final controller is also scored on hidden days that no prompt ever shows. "Best version" always means best on the visible days, the same rule in every arm. Modes (`arms` in the config): `diamond` (every agent proposes approaches alone; everyone scores every idea, without names and shuffled; the script keeps the best few by the others' votes, so nobody manages; each kept idea is built in turns by its author and a partner of another vendor; everyone scores the prototypes; the winner is refined), `alone` (every agent writes and improves its own controller; the best on the visible days is refined by its author; with nine copies of one model this is "the best of N" a single agent gets with the same budget), `orchestra` (a lead splits the job into parts, workers write them, the lead puts them together, then rounds of "lead says what to fix, workers fix, lead puts together"). A diamond arm can set `"share"`: `none` (the default: a builder sees only its own prototype), `scores` (from the second round, also the other prototypes' approach and visible result) or `drafts` (also their whole code); prototypes are built round by round, so everyone sees the same moment. An arm can set its own `repeats`. The study config has six arms: D-mix (4 Claude, 2 Codex, 3 Gemini), D-drafts (D-mix with `share: drafts`, one repeat), D-same (9 Claude), N-mix, N-solo and O, three instances (different days) and 2 repeats; arms take turns going first. For diamonds the run also records whether the group's winner was the best of its prototypes on the hidden days, the gap to that best, what picking by the visible days alone would have given, how alike the prototypes' code is at the first and the last version (overlap of words and names), how votes go to one's own vendor, and how many families of ideas two outside judges (DeepSeek and Qwen by default, not players) find among the first ideas. Output in `~/.agent-dispatch/diamond/<id>/` (or `--out`): `summary.md`, `results.json` and one folder per run (`run.json`, every prompt and reply in `steps/`, every version in `versions/`). Every reply is kept, so a stopped run carries on with the same `--out`; an agent that fails the one-word check sits the run out and the job ends with exit 3. Nothing is published. Design and preregistration: `room/doppio-diamante-design.md` and `lab/influence-plan.md` (row 16) in the project's shared files.

### The game jam (a simplified double diamond)

`node jam.js examples/jam/carolina.json [--out=<folder>] [--labs=claude,codex] [--until=ideas|vote1|build|vote2] [--check]` asks agents from four labs (Claude, Codex, Gemini through Antigravity, Mistral through Vibe) to improve a small game, in four steps, informally, to see what happens (Carlo, 25 Nov). Ideas: every lab reads the game and its README and proposes 3 new features or improvements, alone. Vote: every lab scores the other labs' ideas from 1 to 10, without names and in its own shuffled order; it never sees its own. The 2 ideas with the best average are built. Build: every lab builds the same 2 ideas into the game, alone, in its own git branch (`jam/<lab>`) of a clone in the run folder, and says where to find them. After each build the script opens the game in a headless browser, taps the buttons in `check_clicks` and a few spots, and notes any script errors the original game doesn't have. Vote on builds: every lab reads the other labs' builds (the change, the builder's notes with lab names taken out, the check, the whole game after the change), scores each from 1 to 10 and names the best. To read and vote, agents can only read files in their folder; to build, they can also edit files there, and nothing else: Claude Code with file tools only (`acceptEdits`), Codex in its `workspace-write` sandbox with no network (the only one that can run commands, inside its folder), Antigravity with commands, MCP and web denied, Vibe with its read, write and edit tools only (no bash) and a token cap per step (`mistral_max_tokens`, default 1.5M to read, 6M to build; Vibe prices Mistral models at 0, so its `mistral_max_price` cap never triggers). Models: those of `claude`, `antigravity` and `codex` in `agents.json`; `models` in the config overrides them (Vibe uses its own default model if none is set). `--check` first asks every lab for one tiny read and one tiny write in a scratch folder, to see that its commands work. Output in `~/.agent-dispatch/jam/<stamp>/` (or `--out`): `summary.md` (the ideas, every score, the builds, the vote on builds; authors shown, which the agents never saw), `results.json`, `repo/` with the branches, `patches/<lab>.patch`, screenshots, and every prompt and reply in `steps/`. Replies already there are kept, so a stopped run carries on with the same `--out`. Nothing is pushed or published: a person decides what, if anything, goes to the game's repo. Mistral needs Vibe (`uv tool install --python 3.14 mistral-vibe`) and `MISTRAL_API_KEY`; Gemini uses `GEMINI_API_KEY` when the Antigravity quota is out.

### The Trap

`node trap.js <trap.json>` runs one episode of a puzzle game between two or three agents (`agents`, `names`; Claude and Antigravity by default). Each sets, alone, one puzzle with a short answer, and a private note on why the others will fail. The setter then rereads its puzzle and answer once and may fix them. A fresh run of the setter solves its own puzzle without the answer; if it gets it wrong, the puzzle is void. Each other agent privately states its confidence, then answers. The app, not an agent, compares each answer with the setter's: a right answer is a point to the solver, a wrong one to the setter, a void puzzle to the solver. Then each writes, alone, what it got wrong. The episode is written to `~/.agent-dispatch/traps/<id>/` as `episode.md` and `episode.json`, redacted as above. With a `number` (or `"next"`, one past the highest on the site), it also writes `episode-<n>.md` for the show site, dated `date` or the next Wednesday; with `repo` and `github` (as for a motion) it opens a pull request adding `_traps/episode-<n>.md`, unless `--local`. That pull request is never merged by the app: a person reviews every episode first. Each step may take up to `timeout_min` minutes (25 by default; `AGENT_DISPATCH_STEP_TIMEOUT_MS` overrides it here and in motion.js, where the default is 10).

### Halloween special

`node scare.js <scare.json>` runs a one-off scare-off between two or three agents (`agents`, `names`; Claude, Gemini and Codex by default). For `rounds` rounds (2 by default) each agent writes, alone, one scare of at most `words` words (150 by default; longer is cut there) aimed at the others, with a private note predicting each target's rating. Each target rates it `Scared: 0 to 10` with a short reaction; the ratings a teller gets are its score. From round 2 a teller has read the earlier scares, ratings and reactions, never the notes. Then each writes alone which scare got closest and whether its ratings were honest. The run goes to `~/.agent-dispatch/scares/<id>/` as `episode.md`, `episode.json` and `<slug>.md` (the site file, `slug` "halloween" by default), redacted as above. With `repo` and `github` it opens a pull request adding `_specials/<slug>.md`, unless `--local`; a person reviews it before it is merged.

### Twelve Shapes (pilot)

`node sketch.js <sketch.json>` runs one episode of a drawing game between two or three agents (`agents`, `names`). `words` is one list per round, one word per agent in the order of `agents`. Each drawer gets its word from the app, alone, and draws it as one SVG of at most `shapes` shapes (12 by default; a path counts once per `M` or `m`, so one path can't hold the whole drawing), with no text; a drawing that breaks a rule goes back once with the reason, then is out. Each drawer writes a private note on what it expects the others to guess. The others never see a picture: they get the SVG source with comments, ids, class names and titles taken out. Each states its confidence privately and names the word; the app compares the guess with the word and its `accept` list, ignoring case, articles, punctuation and a plural s. A right guess is a point to the guesser and one to the drawer. Then each writes, alone, what the game showed. The episode is written to `~/.agent-dispatch/sketches/<id>/` as `episode.md`, `episode.json` and `drawings/`, redacted as above. `kinds` names each round ("things", "ideas"). With a `number` (or `"next"`), it also writes `episode-<n>.md` for the show site, dated `date` or today, with the drawings as text; with `repo` and `github` it opens a pull request adding `_shapes/episode-<n>.md`, unless `--local`. A person reviews every episode before it is merged.

### The Relay

`node pair.js <pair.json>` runs a pair-programming session (a private pilot). Codex drives: it works on the task in a throwaway folder, with `codex exec --json -s workspace-write`, so it can write and run commands only in that folder, with no network, and with the laptop's own Codex config and rules ignored. A driver command that would loosen that is refused. The navigator (Claude by default, read-only, from `agents.json`) watches the live event stream: after each file change or command, or every `look_secs`, it sees what happened since its last look and either stays silent or cuts in. A cut-in stops the driver mid-task and resumes the same Codex session with what was said. The driver can write `HELP: <question>` at any moment to pause and ask the navigator. When the driver finishes a turn, the hidden tests (`tests`, run with `proof`) run on a copy of the work inside `codex sandbox`; failures go back to the driver; a pass goes to the navigator, who signs off with `Next: end` or says what's missing. Caps: `max_looks`, `max_rounds`, `max_minutes`. Output in `~/.agent-dispatch/pairs/<id>/`: `episode.md`, `timeline.json`, raw `events.jsonl`, `work/`. `navigator_notes` gives the navigator requirements the driver is never shown (the hidden tests check them), so the driver has to ask or be told: a split spec forces them to work together. Example tasks with hidden tests: `examples/pair/duration/` (easy, no split) and `examples/pair/calc/` (a calculator whose power, percent and error rules only the navigator knows).

`node wrongnote.js examples/pair/wrong-note/wrong-note.json [--agents claude,codex] [--sessions=codex-drives-claude-r2]` is a test of going along (a private pilot). The driver has the written spec; the navigator has the product notes and hands them over at the start, and one note contradicts the spec on purpose (neither agent is told). Every ordered pair of the listed agents plays, `repeats` times, with the wrong note first, middle or last in the list; every model gets the same prompts. Here the driver does not use tools: it writes the whole file in its reply (read-only headless command from `agents.json`, nothing loosened), and the app saves it and runs probe expressions on it, inside `codex sandbox`, after every turn, so the first and last versions show whether the code followed the spec or the note. Hidden tests check the other notes and never the probes. Two judges label the transcript with the names taken out: did the driver raise the conflict, did the navigator concede or insist. Output in `~/.agent-dispatch/wrongnote/<id>/`: `summary.md` (setup, every session, counts by driver and by navigator, limits), `results.json`, one folder per session.

`node relay.js <relay.json>` runs one episode of a team puzzle for three agents (`agents`, `names`; Claude, Antigravity and Codex by default). The app sets the puzzle: five houses, each with a person, a colour and a pet, and a set of clues with one answer where no clue can be dropped (`seed` repeats a puzzle). The clues are dealt between the agents, so no agent, and no pair, can solve it alone. Each writes, alone, what it thinks the others hold. Then `rounds` rounds (3 by default): each agent in turn sends one message, which the app cuts at `words` words (40 by default); with `"rotate": true`, each round starts one speaker later. Each then answers alone with its confidence, and the app checks the order of the five names. All three right is a team win. Last, each writes, alone, who carried the team and whom it wouldn't trust next time. The episode is written to `~/.agent-dispatch/relays/<id>/` as `episode.md`, `episode.json` and `puzzle.json`, redacted as above. Each step may take up to `timeout_min` minutes (15 by default). Nothing is published from here.

## Dispatch (legacy)

`/dispatch` is the first page this repo had: one prompt sent to several agents at once, to compare them. It still works but is no longer developed.

- **Terminal** — each agent opens in its own terminal window, interactive, with the prompt already sent. Inspect and carry on in the tool. When the agent exits, the window stays open in that directory.

## Agents

An agent shows as "not found" until its CLI is on `PATH`. Each one signs in its own way (a session, or an API key named in its `env`); no keys are stored here.

Defaults are in `agents.json`. To change them, copy that file to `~/.agent-dispatch/agents.json`, which takes precedence:

```json
{
  "defaultCwd": "~/code",
  "terminal": ["open", "-a", "iTerm", "{script}"],
  "agents": [
    { "id": "claude", "label": "Claude Code",
      "model": "claude-opus-5-5",
      "interactive": ["claude", "--model", "{model}", "{prompt}"],
      "headless":    ["claude", "-p", "--tools", "Read,Glob,Grep", "--permission-mode", "dontAsk", "--strict-mcp-config", "--", "{prompt}"],
      "env":         ["ANTHROPIC_API_KEY"] },
    { "id": "claude-web", "label": "Claude (web)", "type": "url", "url": "https://claude.ai/new?q={prompt}" }
  ]
}
```

The headless commands that ship here are capped: Claude Code gets only its file-reading tools (`--tools Read,Glob,Grep`), no MCP servers, and refuses anything not pre-approved (`--permission-mode dontAsk`); Codex runs in its read-only sandbox; Antigravity runs in its terminal sandbox with per-session settings that deny file writes, commands, MCP and web access, and disallow non-workspace file access; Cursor starts in Ask mode, which is read-only. Antigravity's `--settings` override is not saved and its deny rules take precedence over user allow rules, so an allowlist in your normal CLI settings cannot widen these headless permissions. Headless agents also get a trimmed environment: `PATH`, `HOME`, locale and proxy settings, plus the variable names listed in the agent's `env` (an API key, if that is how you sign in). Other variables in the shell that ran `npm start` don't reach them.

**Models.** An agent's `model` is the exact model it runs, put in place of `{model}` in its commands. The shipped config pins Claude Code to `claude-opus-5-5` and Antigravity to `gemini-4-argon-medium`, so they do not follow changing CLI defaults. Check Antigravity names with `agy models`: a bare `gemini-4-argon` resolves to the medium tier, so the record would not say which ran. Cursor is intentionally not pinned and uses the installed Cursor CLI's selected default model. A command that uses `{model}` without a `model` is refused. The model shows next to each agent's name on the page, at the top of `transcript.md` and `story.md` (`Models: …`), and in `meta.json`; it records what was asked for, since not every CLI reports what it ran.

**Prompts on stdin.** An agent with `"stdin": true` gets the prompt on stdin, and its headless command has no `{prompt}`. The shipped Codex entry uses it (`codex exec … -`): on macOS, Codex is killed without a word when a prompt of more than about 900 bytes is passed as an argument.

**Antigravity with an API key.** Gemini 4 Argon is a paid-tier model. To run Antigravity on a paid Gemini API key instead of your Google sign-in, set `{ "modelProvider": "gemini" }` in `~/.gemini/antigravity-cli/settings.json` and export `GEMINI_API_KEY` in the shell that runs `npm start`; the shipped config passes that one variable through. If you keep your own `~/.agent-dispatch/agents.json`, add the `model` and `--model {model}` there too.

`{prompt}` is replaced in argv, or URL-encoded into a web agent's `url`. A web agent whose `url` has no `{prompt}` gets the prompt copied to the clipboard instead. Nothing goes through a shell. `terminal` defaults to Terminal.app on macOS and `x-terminal-emulator`/`gnome-terminal`/`konsole`/`xterm` on Linux. The config is read on every request, so edits apply on page reload.

Every dispatch writes `~/.agent-dispatch/runs/<run>/`: `prompt.md`, `meta.json`, a `<agent>.command` script per terminal launch, a `<agent>.log` per background run, and `worktrees/` if isolated. ## Security

Two questions: who can start an agent, and what an agent can do once started.

**What goes on GitHub.** Every show publishes through `publish.js`, for the episode pull request and the Motion's `queue` branch. Commits are made as `Carlo <carlobeschi@users.noreply.github.com>`, whatever the laptop's git identity. The home folder becomes `~` in the title, body and commit message, and the user name, the laptop's git email, a full-name git `user.name`, the macOS full name and the show's `redact` list are scrubbed from them. If a file being published still holds one of these, nothing is pushed. The private terms are read on the laptop and never written to the repo.

**Who can start one.** Only you, from your browser.

- Binds to 127.0.0.1, so it is not reachable from the network.
- Rejects any `Host` other than `localhost`/`127.0.0.1` on its port (DNS rebinding), and any request whose `Origin` is another site.
- Every `/api` call needs the key from `~/.agent-dispatch/key`, which only you can read. The pages don't contain it: the browser gets it once from the link `npm start` prints, in the `#` part, which is never sent to a server. So another site, another user of the machine, or a program in a container that can reach the port can load the pages but can't start an agent or read a conversation.
- Pages cannot be loaded in a frame, run only their own script (a CSP with a per-response nonce), and load nothing from anywhere but this server.
- The config is refused if another user of the machine could change it.
- `~/.agent-dispatch` is made readable only by you: it holds every prompt, log and transcript.
- Dispatch refuses a prompt that starts with `-`, which a CLI would read as an option.

**What an agent can do.** Anything you write, attach or paste, and everything the other agent says, ends up in a prompt. Treat an opener or file from someone else like code from someone else: it can tell the agents what to do. The bounds:

- Conversations and stories run headless with the flags in `agents.json` (see Agents): Claude Code can only read files, Codex is in its read-only sandbox, Antigravity denies writes, commands, MCP and web access in session settings while allowing only workspace file access, and Cursor uses its read-only Ask mode. Antigravity's deny rules override its CLI allow rules; Cursor's Ask mode avoids its default print-mode workspace writes. These are CLI-enforced boundaries, not OS-level isolation for the agent process; Antigravity's sandbox is for terminal commands.
- Each conversation runs in an empty folder. Claude Code can't read outside it; Codex's read-only sandbox can read any file on the machine, though it can't write or reach the network.
- Headless agents get a trimmed environment (see Agents), so keys and tokens in your shell aren't there to be printed.
- Every message heading in a prompt carries a random tag that is removed from whatever an agent writes, so one agent can't write a message that passes for yours. That makes it harder, not impossible, to talk an agent into something; the flags above are what limit the damage.
- Everything in a conversation goes to both agents' providers, including what one agent quotes from a file.
- Attachments are copied, not linked, into a `files/` folder the server creates in the conversation's folder (in a story, the meeting folder; never a home folder, which the agent can change). The server picks the name (no path, no leading dot), never overwrites, refuses to write if `files/` is not a plain folder, and allows only text, code, PDF and image types, 5 MB a file and 20 MB a conversation. Agents get no new permissions to read them.
- Replies are shown as text: Markdown is formatted, HTML never runs, links and images are not loaded. In the saved `.md` files, image syntax and HTML tags in what was said are escaped, so a Markdown viewer doesn't load or render them either.
- A reply is cut at 32 KB.
- The game jam (`jam.js`) is the one script whose agents edit files: only inside their own branch folder in the run folder, with file tools only (Codex: its workspace-write sandbox, no network). See The game jam.
- Dispatch and terminal mode are different: the agent runs in the folder you pick, interactive or headless, with your own CLI settings.

Env: `AGENT_DISPATCH_PORT` (8787), `AGENT_DISPATCH_HOME` (`~/.agent-dispatch`), `AGENT_DISPATCH_CONFIG`.
